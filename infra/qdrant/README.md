# Reel Qdrant operations

Qdrant retrieval and publication are enabled for both Reel Indexing lanes. The indexing PostgreSQL database has been restored to a dedicated PostgreSQL 18.6 + pgvector 0.8.7 container on the same private server and the services now connect to it. A fresh Aiven source dump and matching off-host copy are retained for rollback. Semantic content and workflow state remain in PostgreSQL; existing SQL vector columns are transitional and are not populated by the new candidate writer.

New indexing attempts write vector batches to private R2 staging, commit a generation-fenced SQL publication record, publish and verify the points in Qdrant, then remove the staging bundles when the candidate is finalized. The scraper now queues indexing through the Content service RPC instead of writing semantic tables itself. Its older copied versions must stay disabled.

The latest live cutover checks matched all four semantic tables by count and row-content hash between Aiven and the new database. Projection reconciliation completed with zero pending tasks and zero unready active candidates. The Qdrant retrieval smoke test used the same scoped result IDs before and after the PostgreSQL relocation. A broad new-Reel canary, final removal of SQL vector columns, Qdrant backup/restore proof, and multi-query performance/relevance comparison remain outstanding.

The implementation follows the [pinned v1.20.0 configuration](https://github.com/qdrant/qdrant/blob/v1.20.0/config/config.yaml), [REST query API](https://api.qdrant.tech/v-1-20-x/api-reference/search/query-points), [memory tiers](https://qdrant.tech/documentation/ops-configuration/memory-tiers/) and [snapshots](https://qdrant.tech/documentation/snapshots/). The verified multi-platform image manifest is pinned in Compose. Local Linux tests do not prove native ARM64 operation or homelab capacity.

## Deployment gates

Prepare `QDRANT_SECRET_DIR` outside the shared `.env`, containing `api-key`, `server.crt`, `server.key` and `ca.crt`. Restrict directory and key permissions. Use a CA-signed certificate with DNS SAN `qdrant`; never disable certificate verification. Qdrant and only the two Indexing lanes receive the API key. The common environment file must contain no Qdrant credential. A separate backup operator may receive the same service-owned secret on the designated private network.

The `qdrant` profile starts Qdrant and the dedicated Reel Indexing PostgreSQL database; `docker-compose.qdrant.yml` connects only the Indexing lanes to those services and mounts their secrets. Deploy both Compose files and load the private `.env.qdrant-indexing` alongside `.env` for restarts. That file contains the application database URL and secret-file paths; keep it outside Git. The dedicated database password files must match the URL's app password. Qdrant remains on its private vector network and no PostgreSQL port is published.

The dedicated PostgreSQL container exists because the shared `postgres:18.6` image does not contain pgvector. Keeping Indexing in a separate database container avoids replacing the shared database image or disrupting its other databases. The new container has a 1.5 GiB memory cap and a persistent named volume. The app uses the non-superuser `reel_indexing_app` role; `reel_indexing_admin` is confined to that database service.

Before deployment, verify backing-host AND VM volume free space, allowing the image, WAL, restore copy, rebuild and backups. Require at least 20 GiB in each; retain the existing 12 GiB safety floor. Never prune to meet this gate. The controller requires `VELORA_QDRANT_DISK_PROOF_SHA=<approved-sha>` and `$STATE_DIR/qdrant-volume-proof-<approved-sha>.json` with matching `sha`, numeric `vmFreeGiB >= 20`, `backupRestoreVerified: true` and `benchmarkHoldCleared: true`. These are operator attestations, not substitutes for observing the actual filesystem. Native ARM64 startup, memory during overlapping TEI/indexing and remote backup access remain release gates.

The launcher extracts controller, core and policy from the same approved SHA. Existing Qdrant service/image/network/volume/secret changes are blocked for manual recovery; config-only changes select Qdrant only. The handler converges named volumes without deleting them and checks `/readyz` with verified TLS using OpenSSL already present in the pinned image. Run the authenticated `probe` command after collection initialization and before enabling any writer. Query RPC stays up during `SIGUSR2` job-only drains; the process logs whether in-flight work settled. Resume consumption through a controlled indexing process restart, never by forcing a timed-out drain.

## Owner-service CLI

Run `node scripts/ops/reel-qdrant.cjs <command> --target-label=<reviewed-target>` from an isolated checkout with its own frozen-lockfile dependencies and generated Reel Indexing client. The CLI does not load dotenv or start Nest workers/providers. Supply `REEL_INDEXING_DATABASE_URL`, `QDRANT_URL`, `QDRANT_API_KEY_FILE`, `QDRANT_COLLECTION` and `NODE_EXTRA_CA_CERTS` through a private operator environment. Use a designated client attached to the private vector network and the owner SQL network; do not expose Qdrant host ports. Only disposable loopback tests may set `QDRANT_ALLOW_LOCAL_HTTP=true`.

For a concrete isolated operator runtime, build the existing `builder` stage from the reviewed checkout: `docker build --target builder -f apps/reel-indexing-service/Dockerfile -t velora-reel-qdrant-ops:<sha> .`. That stage installs the frozen lockfile and generates its own Reel Indexing client; it includes ts-node, tsconfig-paths and the source CLIs. Override the entrypoint to `node`; do not run the service startup command or migrations. Create a one-shot container on `<project>_microservices-net`, attach `<project>_reel-vector-net` with `docker network connect` before starting it, then use `docker start -a` and remove only that operator container. Bind the API-key and CA files read-only at the paths named in the private operator env file, and bind a private artifact/backup directory at `/work`. Set `NODE_EXTRA_CA_CERTS` before Node starts. This gives the CLI both owner-SQL connectivity and private `https://qdrant:6333` DNS without publishing ports or giving credentials to AI/Content. No operator image build, network attachment or remote mount was performed against production here.

Commands that mutate SQL or Qdrant require `--confirm=QDRANT_<target-label>`:

1. `initialize` explicitly creates the physical collection, typed payload indexes and alias. Startup never creates or repoints them. `probe` checks authenticated physical collection identity and `/readyz`.
2. Enable `INDEX_VECTOR_PROJECTION_ENABLED=true` in both lanes while publication stays false and reads stay PostgreSQL, using the separately reviewed operator rollout. Prove all old writers are drained or every writer, delete consumer and both lanes capture mutations. Run `enroll --capture-proof=ALL_WRITERS_DRAINED_OR_CAPTURE_ENABLED --max-tasks=100` repeatedly until no candidates remain unenrolled. Enrollment uses the persistence lock and never replaces a concurrently enrolled generation.
3. `export --directory=<new-immutable-directory>` reads all four SQL vector tables, active and inactive, in one read-only repeatable-read snapshot. It writes complete SQL records and points in checksummed batches of 128 and publishes `complete.json` only on success. Never resume an incomplete export from a different snapshot; keep it and choose a new directory.
4. `import --directory=<completed-export> --receipts=<new-receipt-directory>` validates checksums and provenance, rejects superseded/deleted generations against current SQL, and uploads at most 128 points with one batch in flight. Resume using the same receipts; replays are idempotent and recheck SQL. `--dry-run=true` validates/counts without writes or receipts. Import does not certify readiness.
5. `reconcile --max-tasks=100` runs leased live projection work and verifies full current manifests. Exit 2 means pending work or unready active candidates remain; success requires zero of both. Do not infer transaction completion from a maximum task sequence. `status` observes durable lag without Qdrant writes.

Point UUIDs hash the JSON tuple of kind, Reel, attempt, lossless generation string and stable document ID. Candidate replacement always advances generation, including same-attempt retries. Cosine vectors are validated after normalization within absolute component tolerance `2e-5`; distance remains `1 - similarity`, including negative similarity. SQL lexical/tag fusion keeps RRF60. Exact boundary ties may order equivalently scored vectors differently; no latency/relevance improvement is claimed.

## Backup and restore

`node scripts/ops/qdrant-backup.cjs backup --target-label=<target> --confirm=QDRANT_<target> --directory=<local-private-dir> --offhost-directory=<verified-remote-mount> --offhost-proof=VERIFIED_REMOTE_MOUNT_AND_ACCESS --sql-backup-proof=<complete-export-or-compatible-SQL-proof> --encryption-key-file=<private-random-key>` creates a bounded collection snapshot, encrypts snapshot plus provenance with scrypt/AES-256-GCM, copies to a separate verified remote filesystem and verifies ciphertext readback before rotation. Keep the key outside both backup destinations. The tool retains three owned local archives and seven owned off-host archives, and removes its Qdrant snapshot only after success. It never deletes unrelated files. The SQL proof must match the explicit owner database and include snapshot provenance; this does not make the snapshot cross-database atomic.

The maximum snapshot is 128 MiB and archive 180 MiB; larger snapshots fail safely with retained artifacts. Qdrant's server body limit is 160 MiB for snapshot upload; ordinary vector requests/responses remain capped at 4 MiB, batches at 128 and candidate manifests at 20,000 points. Backup runs in a separate bounded operator process; it currently buffers the archive, so reserve memory for encryption and restore. Schedule daily only after verifying the intended remote mount, access and retention; `--local-test=true` is a loopback-only simulation and explicitly reports `offhostVerified=false`.

For recovery: switch every reader to PostgreSQL, drain Qdrant reads, then disable publication enforcement and drain writers. `restore --target-label=<target> --confirm=QDRANT_<target> --archive=<archive> --encryption-key-file=<key> --recovery-proof=READERS_POSTGRES_WRITERS_DRAINED_PUBLICATION_DISABLED` authenticates/decrypts/checksums first, durably sets maintenance and invalidates readiness before upload. It rebuilds the expected alias if missing and refuses a different physical target. Failure leaves maintenance enabled. After authenticated identity and restore validation, run `reel-qdrant.cjs resume --confirm=QDRANT_<target> --target-label=<target> --recovery-proof=RESTORED_AND_ALIAS_VERIFIED`, then reconcile until complete. Resume advances the epoch and replays obsolete-generation deletion immediately. Never enable reads from restored certificates.

## Monitoring and cutover

The `metrics` command emits dependency readiness, observed memory/error counts, projection pending/lag and a freshness timestamp without payloads or credentials. `--storage-path=<mounted-volume>` adds observed filesystem availability; without a real mounted volume storage stays unmeasured. Atomically publish output through the existing node-exporter textfile directory; never leave partial output. The optional Prometheus rules gate dependency/lag alerts on projection enabled and explicitly alert on stale data. No scheduler or backup destination is enabled by this change.

Before moving the Indexing SQL database, both job lanes must be idle and all `PROCESSING` attempts must be dispositioned. The Aiven source dump and off-host copy are retained for rollback. The new same-server database restore was checked against source table counts and content hashes; both service lanes now use it with Qdrant retrieval and publication enabled.

## Qdrant-only embeddings

The additive `20261103100000_stage_qdrant_only_embeddings` migration makes candidate SQL vectors nullable and stores private R2 bundle references in the durable publication journal. New semantic candidates put vector arrays in immutable R2 staging, commit metadata and generation state to PostgreSQL, then publish and verify Qdrant points. Finalized publications delete the staged vector bundle. Embedding-cache batches also use verified R2 staging; the operator migrates preexisting cache arrays with `node scripts/ops/migrate-embedding-cache.cjs --target-label=homelab --confirm=EMBEDDING_CACHE_homelab`.

The final migration still needs to drop the four semantic-table embedding columns, the embedding-cache JSON column, and the HNSW indexes after a new Reel canary, interruption/recovery checks, access/lexical parity, and Qdrant backup/restore proof pass. Keep semantic text, lexical indexes, attempts, and lifecycle state in PostgreSQL. Qdrant is the vector search/store; SQL no longer serves as vector fallback. Preserve the Aiven source backup for comparison and rollback evidence; do not delete it as part of the database switch.
